# 日报审核、通知、导出与资源权限设计

日期：2026-08-24  
状态：已确认；负责人指派补充规则待最终审阅

## 1. 目标

本轮改造解决以下问题：

1. 修复日报附件上传完成区域中文件名、进度条、百分比和状态文字重叠。
2. 让所有有效组织角色都能查看并新增“资源与耗材”，新增时可保留自己为负责人或指定其他在职员工。
3. 让直属 Project Leader 和管理层能够打开授权范围内的成员日报详情、下载有权限的附件、添加评论和确认日报。
4. 在账户菜单内新增通知中心，用未读红点提醒日报评论和确认消息。
5. 允许日报作者及有权查看该日报的 Project Leader/管理层导出 PDF 或 Word。

本轮不包含邮箱确认、忘记密码/重置密码、资源问题邮件发送改造。这些作为后续独立项目处理。不得创建虚假生产员工或演示数据。

## 2. 已确认的业务规则

### 2.1 日报可见范围

- 员工只能查看自己的日报、评论、附件和通知。
- Project Leader 只能查看与自己负责的 Objective/KR 相关的员工日报。日报条目必须关联到该 Project Leader 负责 Objective 下的 KR，不能仅凭同项目成员关系扩大可见范围。
- 管理层可以查看当前组织的全部日报，包括 Project Leader 的日报。
- `administrator` 仅代表系统管理员，不自动获得业务日报查看、评论或确认权限。
- 所有数据库读取、评论、确认和附件下载权限必须在服务端/RLS/RPC 校验，不能只依赖前端隐藏按钮。

### 2.2 评论与确认

- 有权查看日报的直属 Project Leader 和管理层可以添加评论。
- 评论不会修改员工填写的日报内容。
- 评论保留审计记录；普通用户不能物理删除或篡改历史评论。
- 第一个有权限的 Project Leader 或管理层确认日报后，日报立即进入 `confirmed` 并锁定正文和附件。
- 已确认日报仍允许有权审核者继续追加评论。
- 重复确认是幂等操作：返回“日报已确认”，不重复产生确认通知。

### 2.3 资源与耗材

- 所有有效角色均可查看、搜索、查看资源详情、报告问题和添加资源。
- 添加资源时“资源负责人”默认是当前添加人；添加人也可以指定同组织、已审核且在职并具有 active role 的员工为负责人。
- 创建人和资源负责人分别保存：`created_by` 永远记录添加人，`owner_id` 记录最终负责人。
- 指定自己为负责人时不产生通知；指定其他员工时，在资源创建成功的同一事务内向该员工生成一条负责人指派通知。
- 资源负责人、管理层和管理员可以修改资源。
- 只有管理层和管理员可以归档资源。
- HR、员工等角色的新增资源行为仍受组织隔离、字段校验、密级和附件安全规则约束。

### 2.4 导出

- 日报作者本人，以及有权查看该日报的 Project Leader/管理层，可以导出 PDF 或 Word。
- 导出包含：填写人、日期、状态、总工时、全部 Daily OKR 条目、审核信息、评论及附件清单。
- 附件原文件不嵌入 PDF/Word；导出只列出附件显示名称、密级等获授权元数据，避免文档过大或绕过附件下载授权。
- 文件名格式为 `日报-姓名-YYYY-MM-DD.pdf` 或 `日报-姓名-YYYY-MM-DD.docx`。

## 3. 数据模型

### 3.1 `daily_report_comments`

建议字段：

- `id uuid primary key`
- `organization_id uuid not null`
- `report_id uuid not null`
- `author_id uuid not null`
- `body text not null`
- `created_at timestamptz not null`

约束与安全：

- 评论正文去除首尾空白后不能为空，并设置合理长度上限。
- 组织、日报和评论者必须属于同一组织。
- 浏览器仅通过受控 RPC 新增评论。
- 普通 `authenticated` 用户不能直接更新或删除评论。
- 读取评论沿用日报详情可见规则。

### 3.2 `user_notifications`

建议字段：

- `id uuid primary key`
- `organization_id uuid not null`
- `recipient_id uuid not null`
- `actor_id uuid`
- `notification_type`：本轮包含 `daily_report_comment`、`daily_report_confirmed`、`resource_owner_assigned`
- `report_id uuid`
- `resource_id uuid`
- `comment_id uuid`
- `read_at timestamptz`
- `created_at timestamptz not null`

约束与安全：

- 用户只能读取并标记自己的通知。
- 评论 RPC 与确认 RPC 在同一事务内创建通知，避免业务数据成功而通知丢失。
- 确认通知设置幂等约束，重复确认不得重复插入。
- 资源负责人指派通知只发送给被指定的其他员工，`actor_id` 记录添加人，`resource_id` 指向新资源。
- 模型允许后续扩展资源问题、邮件状态等通知类型，但本轮不实现这些类型。

## 4. 服务端接口与授权

需要提供受控接口，名称可以按仓库现有命名规范调整：

- `get_daily_report_detail(report_id)`：返回授权后的日报基本信息、Daily OKR 条目、可见附件元数据、审核信息和评论。
- `comment_daily_report(report_id, body)`：校验直属 Project Leader/管理层权限，插入评论并通知日报作者。
- `confirm_daily_report(report_id, expected_revision)`：沿用现有确认原子性，补齐直属 Project Leader/管理层范围和确认通知。
- `list_my_notifications(limit, cursor)`：只返回当前用户通知，支持分页。
- `mark_notification_read(notification_id)` 与 `mark_all_notifications_read()`：只能更新当前用户通知。
- `list_eligible_resource_owners()`：只返回当前组织已审核、在职且具有 active role 的员工。
- 新增资源接口接受显式 `owner_id`；缺省或等于当前用户时由当前用户负责，指定他人时服务端验证候选资格并原子写入负责人通知。为避免破坏已部署客户端，保留现有“创建人即负责人”的 RPC 签名，并新增带 `owner_id` 的明确签名供新版前端调用。

直属 Project Leader 的服务端判定路径为：

`daily_report -> daily_okr_blocks -> key_results -> objectives -> objective.owner_id`

只要日报至少一个条目关联到该 Project Leader 负责 Objective 下的 KR，该 Project Leader 可以查看该日报详情；接口返回的条目范围必须保持一致，不能借一个获授权条目读取其他无关、密级更高或其他负责人范围内的敏感内容。管理层按组织范围读取，仍需通过密级校验。管理员不自动通过该检查。

附件下载继续调用现有下载授权接口，不在详情响应中暴露永久公开 URL、Storage 凭据或 OSS AccessKey。

## 5. 前端设计

### 5.1 上传状态排版

- 文件名单独占据可伸缩区域，过长时省略号显示，并通过 `title` 或可访问名称提供完整文件名。
- 进度条、百分比和状态使用独立布局列，不与文件名重叠。
- 窄屏下改为纵向换行。
- `100%` 仅代表传输字节完成；只有服务器 finalization 成功后显示“上传完成”。

### 5.2 日报列表和详情弹窗

- “我的日报”和“项目成员日报”都以摘要行展示。
- 授权行提供“查看详情”；点击后按需加载完整详情并打开 modal/dialog。
- 弹窗展示填写人、日期、状态、总工时，以及每组 Daily OKR 的当日 Objective、关联 Objective/KR、工作描述、结果、工时和附件。
- 附件仅在当前用户通过下载授权时显示下载动作。
- Project Leader/管理层在弹窗底部看到评论输入和确认按钮；员工只读查看评论。
- 已确认日报隐藏或禁用重复确认动作，但评论入口继续可用。

### 5.3 导出

- 弹窗提供“导出 PDF”和“导出 Word”。
- 在浏览器端根据已经授权返回的详情数据生成文件。
- 导出失败只显示错误，不改变日报、评论、通知或确认状态。
- 导出实现必须支持中文字体/字符，并对用户填写内容做安全转义。

### 5.4 通知中心

- 通知入口位于左下角账户菜单，不新增侧边栏导航项。
- 账户圆框右侧在存在未读消息时显示红点，并提供可访问的未读数量说明。
- 账户菜单包含“消息通知”和未读数量；点击打开通知面板。
- 支持单条标记已读和全部标记已读。
- 点击日报通知时先标记已读，再打开对应日报详情。
- 点击资源负责人指派通知时先标记已读，再打开对应资源详情。
- 如果日报当前已不可访问，通知仍可标记已读，并显示“该日报当前不可查看”。

### 5.5 资源负责人选择

- “添加资源”表单显示单个负责人下拉框，默认选中当前添加人，不增加额外开关。
- 下拉框只显示服务端返回的同组织合格员工；加载失败时不得允许用未经验证的自由文本负责人继续提交。
- 选择其他员工后，提交按钮仍执行一次原子创建；成功后被指定员工在账户圆框看到未读红点和负责人指派消息。

## 6. 数据流

1. 列表只加载日报摘要，避免一次返回全部正文和附件。
2. 用户点击详情后，前端调用详情 RPC。
3. 服务端按组织、角色、Objective/KR 领导关系和密级过滤返回内容。
4. 评论或确认通过独立 RPC 写入；RPC 在同一事务创建对应通知。
5. 日报作者刷新列表/通知中心后读取自己的未读通知和最新锁定状态。
6. 点击通知跳转详情；附件下载再次经过单独授权。
7. PDF/Word 仅使用详情 RPC 已授权数据生成。
8. 添加资源时，前端先读取符合资格的负责人；提交后服务端同时创建资源和必要的负责人通知，任何一步失败都整体回滚。

## 7. 错误与并发处理

- 无查看权限统一返回权限错误，不泄露目标日报是否存在。
- 附件密级不足时允许查看有权限的日报文字，但不返回该附件下载能力。
- 评论提交失败时保留输入内容并允许重试。
- 确认使用 revision 乐观锁；日报已更新时要求审核者重新加载。
- 并发确认只允许第一次状态转换创建确认通知，其余请求返回已确认结果。
- 通知读取失败不阻止用户使用其他页面；红点保持上一次可靠状态或显示加载失败。
- 指定的资源负责人已失效、未审核、跨组织或没有 active role 时拒绝创建资源，不退回为添加人，也不创建残缺资源或通知。
- 导出失败不写数据库。

## 8. 测试与验收

### 8.1 数据库 pgTAP

- 作者本人读取自己的日报详情。
- 直属 Project Leader 读取、评论和确认其负责 Objective/KR 下员工的日报。
- 非直属 Project Leader 被拒绝。
- 管理层读取、评论和确认全组织员工及 Project Leader 日报。
- 管理员角色单独不能读取、评论或确认业务日报。
- 评论和确认在同一事务生成正确接收人的通知。
- 重复确认不产生重复通知。
- 用户只能读取和标记自己的通知。
- 详情和附件仍遵守密级与组织隔离。
- 所有角色可添加资源；资源修改和归档遵守已确认规则。
- 添加人默认成为负责人；指定有效的其他员工后 `created_by` 与 `owner_id` 正确分离并只生成一条负责人通知。
- 跨组织、inactive、pending 或无 active role 的负责人被拒绝，资源和通知均不落库。

### 8.2 前端测试

- 上传文件名、进度、百分比和状态不重叠；长文件名和窄屏可用。
- 所有角色显示资源导航并能打开添加资源表单。
- 负责人选择默认当前用户；选择他人后提交参数正确，并在对方账户通知中心出现可打开资源详情的消息。
- 日报详情弹窗按权限显示评论、确认、下载和导出动作。
- 通知红点、未读数量、单条已读、全部已读和通知跳转正确。
- PDF/Word 导出包含中文日报内容、评论和附件清单。

### 8.3 角色同步 QA

执行以下隔离场景，不创建虚假生产员工或演示数据：

1. 员工提交日报。
2. 直属 Project Leader 查看详情、下载获授权附件并评论。
3. 员工看到未读红点，打开通知并查看评论。
4. Project Leader 或管理层确认日报。
5. 员工刷新后看到确认通知和锁定状态。
6. 管理层查看并确认 Project Leader 日报。
7. 作者和授权审核者分别导出 PDF、Word。
8. 员工新增资源并指定另一名有效员工；被指定人收到红点通知，点击后打开资源详情。

## 9. 部署与回滚原则

- 使用 additive migration 创建评论、通知、索引、RLS 和 RPC；不改写已部署 migration。
- 新前端上线前先应用数据库迁移并 reload PostgREST schema。
- 回滚前端时不得重新开放旧的不安全日报 RPC。
- 如需止血，可撤销评论/确认/通知写 RPC 的 `authenticated EXECUTE`，保留只读详情能力。
- 不在 Git、前端构建、Nginx 或文档中写入 service-role key、数据库密码或 OSS AccessKey。
