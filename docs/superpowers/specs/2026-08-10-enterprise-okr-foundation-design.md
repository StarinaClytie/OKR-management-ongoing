# 企业 OKR 管理系统基础设计

## 1. 目标与范围

第一版建设一个中文企业级 OKR 管理系统前端基础，风格参考 Microsoft Viva Goals、Jira 和 Monday.com。重点交付 UI 结构、路由、可复用组件、模拟数据、角色权限架构和角色化 Dashboard；暂不实现后端、真实身份认证、数据库、文件加密服务或 AI 校验。

本设计结合项目内的会议记录、OKR 使用手册、OKR 表单、SMART 检查表、OKR 检查清单、周报模板和项目说明。业务重点包括：Objective 与项目关联、KR 作为可度量执行项、日报关联 O/KR 与工时、主张需要原始数据佐证、周报记录延期原因与解决方案，以及项目总览和甘特图。

## 2. 技术方案

- React + TypeScript + Vite
- React Router：页面路由与受保护路由
- Context + 配置驱动服务：模拟身份、权限判断和角色切换
- CSS 设计令牌与可复用组件：企业级浅色界面、响应式布局
- 前端模拟仓储：用户、项目、OKR、报告、文档和审计数据
- 前端测试：权限规则、路由、角色视图和关键交互

第一版不引入完整策略引擎。权限 API 保持独立，以便未来将前端模拟权限替换为后端 RBAC/ABAC 决策。

### 2.1 简单易用原则

系统的功能深度不能转化为用户操作复杂度。第一版遵循渐进式披露：默认只展示当前角色、当前任务和当前项目最相关的信息，专业分析和高级操作按需展开。

- 常用任务优先：填写日报、更新本人 KR、查看风险和确认成员日报应从 Dashboard 一步到达。
- 角色化默认值：用户进入页面后自动获得合适的数据范围和视图，不要求先理解复杂筛选器。
- 一屏一个主目标：页面顶部明确主操作，次要操作降低视觉权重。
- 统一交互：状态、进度、负责人、密级和权限提示在所有模块采用一致表达。
- 减少专业术语：使用员工熟悉的中文标签，并在必要处提供简短说明。
- 高级视图按需出现：五种可视化全部提供，但不同时铺满首屏；使用清晰标签切换。
- 安全提示不打断常规工作：仅在查看、下载、导出或变更权限等敏感动作时提供必要说明。
- 空状态给出下一步：没有 OKR、日报或项目数据时，提供清晰的可执行入口。

## 3. 角色与工作归属

系统包含五个角色：

1. Administrator（管理员）
2. Management（管理层）
3. Project Leader（项目负责人）
4. Employee（员工）
5. HR

角色不等同于业务归属。数据模型分别表达：

- `objectiveOwner`：Objective 总负责人
- `keyResultOwner`：KR 实际执行负责人
- `projectLeader`：项目管理负责人
- `reportAuthor`：日报或周报填写人

同一用户可以同时拥有多个工作归属。项目负责人既可管理项目，也可亲自承担 KR、更新进度并填写自己的日报。

## 4. 权限架构

### 4.1 判定模型

权限判断采用“角色能力 + 数据范围 + 密级 + 操作”的组合模型：

```text
can(user, action, resource) =
  roleCapability
  AND scopeMatch
  AND classificationAllowed
  AND resourceCondition
```

- 角色能力：是否具备查看、创建、编辑、确认、导出或授权等操作能力。
- 数据范围：本人、所属项目、所属团队、部门、全公司或系统元数据。
- 密级：公开、内部、机密、严格机密。
- 资源条件：是否为作者、负责人、项目成员、审批人，或是否获得临时授权。

### 4.2 管理员职责分离

管理员可以管理用户、角色、权限、系统配置和审计元数据，但默认不能阅读项目机密正文。管理员只有在同时具备项目成员身份，或获得具有审计记录的临时授权时，才能访问对应正文。

### 4.3 受控操作

以下操作使用独立权限，不因拥有一般查看权限而自动开放：

- 查看机密正文
- 下载附件
- 导出 OKR、日报或周报
- 修改文档密级
- 修改项目成员权限
- 查看跨项目工时明细
- 授予临时访问权限

所有受控操作预留审计事件接口。第一版使用模拟事件记录，未来由后端强制执行和持久化。

### 4.4 前端安全边界

前端的菜单隐藏、路由拦截和按钮禁用仅用于用户体验与架构演示，不视为真实安全控制。未来后端必须对每次资源读取、更新、下载和导出重新鉴权，并负责文件存储加密、传输加密、审计、防篡改和授权失效。

### 4.5 公开透明与分级可见性

OKR 基础信息默认强调组织透明，但“OKR 基础信息、日报详情、附件内容”是三个独立资源层级，不能因为可查看 OKR 就自动获得附件权限。

- 最高管理层可以查看组织内所有人员的 O、KR、进度、日报详情以及密级允许查看的附件。
- 直接上级和直线间接上级可以查看其全部下级的 O、KR、进度和日报详情；附件继续按密级判断。
- 下级可以查看直接或间接上级直至 CEO 的 O、KR、负责人、进度和状态，但不能查看上级日报正文、工时证据或附件。
- 同一项目成员可以互相查看 O、KR、进度和日报详情；附件继续按密级判断，不因同项目身份自动开放机密或严格机密文件。
- 与工作有关联但不在同一项目的人员可以查看基础 OKR 信息；日报和附件只有在系统存在明确协作关系或被主动共享时才可查看。
- 无直接工作关系的普通员工只查看组织允许公开的基础 OKR 信息，不查看日报详情和附件。

“基础 OKR 信息”固定包含 Objective 内容、KR 列表、KR 负责人、完成进度和状态。日报正文、工时细节、证据和附件不属于基础 OKR 信息。

公开透明规则仍受密级覆盖：公开信息组织内可见；内部信息按项目或授权关系可见；机密信息仅指定角色或人员可见；严格机密信息必须明确授权，不能通过管理层、上下级、同项目或协作关系自动获得。客户数据、合同、个人信息、薪资和关键项目文件应使用机密或严格机密级别。

## 5. 权限矩阵

| 功能 | 管理员 | 管理层 | 项目负责人 | 员工 | HR |
|---|---|---|---|---|---|
| Dashboard | 系统状态与权限审计 | 公司/部门全局 | 所属项目与本人执行项 | 个人工作 | 人员、工时与组织 |
| OKR 管理 | 规则配置；不默认读机密正文 | 查看与审批授权范围 | 管理所属项目；更新本人 KR | 查看并更新本人 KR | 查看授权组织汇总 |
| 项目 | 配置与授权 | 查看公司或部门项目 | 管理所属项目 | 查看参与项目 | 查看人员配置 |
| 日报 | 配置与审计 | 查看授权汇总/明细 | 填写本人日报；查看、评论、退回或确认项目成员日报 | 填写和管理本人日报 | 提取授权工时字段，不默认看机密正文 |
| 周报 | 配置与审计 | 查看授权范围 | 创建和管理所属项目周报 | 查看相关周报 | 查看组织摘要 |
| 团队 | 用户与角色管理 | 查看组织 | 管理项目成员 | 查看所在团队 | 管理人员资料 |
| Analytics | 系统使用与权限异常 | 公司级分析 | 项目分析 | 个人分析 | 人力与工时分析 |
| Settings | 系统设置 | 个人偏好 | 项目及个人偏好 | 个人偏好 | HR 规则及个人偏好 |

项目负责人不得修改成员的原始日报，但可以评论、退回或确认。所有状态变化保留原始作者和操作记录。

## 7. Dashboard 设计

### 7.1 视觉方向

采用确认的 B × C 融合方案：浅色侧边栏、行动优先的顶部区域、双列 Widget 布局和专业项目可视化区域。

- 顶部回答“今天最重要的是什么”。
- 项目负责人同时看到“我负责的项目”和“我亲自执行的 KR”。
- 主区域使用模块化 Widget；复杂图表在移动端显示摘要与详情入口。
- 机密 Widget 显示密级标签；无权限内容不泄露标题、摘要或计数。
- 图表使用浅色背景、深色文字、克制的蓝色主色，并通过文字、线型、形状和位置补充颜色编码。

### 7.2 角色 Dashboard

- 管理层：公司 OKR 健康度、目标进度、风险项目、部门对齐、趋势、近期更新。
- 项目负责人：今日重点、本人 KR、项目进度、成员日报、里程碑、风险、团队负载和下一检查节点。
- 员工：本人 OKR、今日任务、日报快捷入口、个人工时、个人趋势和授权项目计划。
- HR：人员投入、项目工时、日报提交率、团队负载和组织分布；不默认展示机密业务正文。
- 管理员：用户、角色、权限异常、审计记录和系统配置状态；不展示机密业务正文。

### 7.3 日报填写体验

日报不是一段自由文本，而是以“当日 O → 多个当日 KR → 每个 KR 的投入和结果 → 关联周期 OKR → 成果附件”为主线的结构化记录。用户填写独立的当日 O，同时可以选择关联已有季度、项目或个人 OKR；两者不是互斥关系。

默认表单仅显示当前步骤所需字段，使用渐进式披露降低学习成本：

1. 填写当日 O。输入框旁只显示一句“建议使用动词＋结果描述今天最重要的目标”，并提供三个可直接参考的短例子；完整写法折叠在“查看更多写法”中。
2. 添加 KR1、KR2 等当日关键结果。每个 KR 先选择度量类型，再显示该类型需要的字段；用户可以增删或排序 KR。
3. 为每个 KR 填写本日工时、当前值或状态、工作说明和完成度。完成度默认由系统根据度量类型计算，不要求用户随意猜测百分比。
4. 可选关联已有 O 或 KR，用于把当天工作汇入季度或项目进度。关联不覆盖当日 O/KR 原文。
5. 最后添加成果附件、链接或证据，并为每一项独立选择密级。

O 的帮助内容采用手册中的四种写法，但一次只展示少量示例：

- 动词＋名词，例如“优化销售流程”。
- 动词＋形容词＋名词，例如“打造旗舰产品”。
- 副词＋动词＋名词，例如“大幅提升品牌影响力”。
- What＋Why，例如“完成原型验证，为产品评审提供依据”。

O 通常使用定性描述、以明确动词开头、责任范围可控、在当前周期内可完成且尽量不超过 20 个字。避免“协助、参与、支持”等责任不明确的动词。第一版只给提示，不阻止用户保存。

KR 提供四种度量类型，并根据选择切换右侧 Information 和输入字段：

- 数量型：填写目标值和当前值；完成度为“当前值 ÷ 目标值”，最高按 100% 展示。
- 比率型：填写起始值、目标值和当前值；完成度按目标方向计算，界面必须说明“提升”和“提升至”的基准差异。
- 里程碑型：填写截止日期，并在“未开始、进行中、已完成”中更新；最终评分完成为 100%、未完成为 0%，进行中可显示过程状态但不伪造最终评分。
- 主观型：仅在难以量化时使用；必须先填写清晰、可共同判断的验收标准，再选择 0～1 分。

系统默认建议数量型，但只提供建议，不自动改变用户选择。可根据文本给出轻量提示：出现“截至、上线、交付、完成”时建议里程碑型；出现“提升至、降低至、增长”时建议比率型。右侧 Information 只展示当前字段的一个公式、一个例子和一个注意点，完整规则放在折叠帮助中。

O 的汇总进度默认取其 KR 完成度平均值。用户可以手动调整自动计算结果，但必须填写调整原因并保留模拟审计记录。评分用于持续跟踪而非直接绩效奖惩，填写过程应控制在几分钟内。

第一版不加入 AI 检查按钮或伪 AI 功能。领域结构和校验接口需支持未来接入质量建议：检查 O 是否清晰、KR 是否可衡量、KR 是否支撑 O，以及 KR 是否只描述任务而未描述价值。未来 AI 只能给出建议，不能自动覆盖员工原文。

## 8. 五种项目可视化

第一版全部实现为可复用 Widget，并使用同一套模拟领域数据。

### 8.1 OKR 对齐树

展示公司 O、项目 O、KR 和负责人之间的层级与对齐关系。突出当前用户亲自承担的 KR，并支持按权限隐藏受限节点内容。

### 8.2 甘特图

展示 KR、任务、里程碑、依赖和下一检查节点。实际时间条与基准计划使用不同线型或填充，不只依靠颜色区分。

### 8.3 进度趋势

按周展示实际进度与计划进度。模拟数据提供至少 12 个周度点，避免用少量点制造虚假的趋势感。标题、时间范围、单位和计划基准清晰可见。

### 8.4 风险矩阵

使用发生概率 × 业务影响定位项目风险。风险同时使用位置、文字和标记表达；颜色仅作为辅助。点击风险进入授权范围内的详情。

### 8.5 工作负载

按成员比较计划工时、已记录工时和可用容量。项目负责人查看所属项目成员；员工查看本人；HR 只查看授权的工时与容量字段，不默认看到机密工作内容。

## 9. 组件边界

### 9.1 应用与权限

- `AppShell`：顶栏、浅色侧边栏和内容区域
- `AuthProvider`：当前模拟用户和角色切换
- `ProtectedRoute`：路由权限
- `PermissionGate`：组件或操作权限
- `PermissionService`：统一权限计算
- `ConfidentialityBadge`：密级标记
- `RestrictedContent`：无权内容的安全占位

- `DashboardPage`：读取角色 Dashboard 配置
- `DashboardGrid`：响应式 Widget 布局
- `DashboardRegistry`：Widget 类型注册表
- `WidgetTabs`：五种项目视图切换
- `AlignmentTreeWidget`
- `GanttChartWidget`
- `ProgressTrendWidget`
- `RiskMatrixWidget`
- `WorkloadWidget`

### 9.3 业务基础组件

- `MetricCard`
- `ProgressBar` / `ProgressRing`
- `StatusBadge`
- `OwnerAvatar`

非 Dashboard 路由在第一版提供结构完整的页面框架、权限状态、筛选区、示例列表和空状态，不实现真实提交或持久化业务流程。

## 10. 模拟数据模型

模拟数据覆盖：

- 用户、角色、部门、团队和项目成员关系
- 项目、Objective、Key Result、负责人和贡献者
- 日报、周报、评论、确认状态和工时
- 里程碑、依赖、检查节点和周度进度快照
- 风险、概率、影响、负责人和处置状态
- 文档、附件、密级、授权范围和导出权限
- 审计事件和临时授权

数据集中必须包含：项目负责人亲自执行 KR 的案例、员工执行 KR 的案例、延期项目、超负载成员、机密文档、管理员无正文权限，以及 HR 仅可访问工时字段的案例。

## 11. 状态与错误处理

- 无权限：显示访问受限页面或安全占位，不泄露受限资源摘要。
- 模拟数据缺失：显示明确空状态。
- Widget 配置错误：显示局部错误边界，其他 Widget 继续工作。
- 未知角色或权限：默认拒绝访问。
- 导出受限：说明所需授权，不生成文件。
- 图表数据不足：退化为 KPI、列表或说明，不绘制误导性趋势图。

## 12. 测试方案

### 12.1 权限测试

- 五个角色的导航项目符合权限配置。
- 无权限地址进入访问受限页。
- 管理员可管理权限，但默认不能读取机密正文。
- HR 可查看授权工时字段，但不能读取项目机密内容。
- 项目负责人可填写自己的日报并更新自己的 KR。
- 项目负责人可查看、评论、退回和确认所属项目成员日报，但不能修改原始正文。
- 员工只能修改自己的日报和 KR。
- 导出、下载和查看机密正文分别鉴权。
- 最高管理层和上下级关系按透明度规则获得相应的基础信息或详情权限。
- 下级查看上级时只能看到基础 OKR 信息，不能看到日报正文、证据和附件。
- 同项目成员可查看彼此日报，但机密与严格机密附件仍需独立授权。
- 跨项目协作者只有在存在明确协作关系或主动共享时才能查看日报或附件。

### 12.2 Dashboard 与可视化测试

- Management、Project Leader、Employee 和 HR 获得不同 Widget 组合。
- 管理员获得系统管理 Dashboard，不展示业务机密正文。
