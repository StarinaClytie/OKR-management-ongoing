# 日报 KR 关联与工时可见范围设计

## 背景

当前员工仪表盘能够显示通过 `kr_assignments` 分配给自己的 KR，但填写日报时，“关联季度 KR”下拉框可能只显示“不关联 KR”。同时，仪表盘工时视图无法稳定表达员工本人、项目负责人及项目成员之间的工时查看范围；日报页面的“添加另一组 OKR”按钮也会在当前组未完成时完全消失，容易被误解为功能被移除。

本次设计统一日报、KR 分配、项目归属与工时读取规则，并保持日报无需关联 KR 即可填写的产品原则。

## 已确认的业务规则

### 1. 日报可关联的 KR

- “关联季度 KR”下拉框第一项始终为“不关联 KR”。
- 其余选项来自当前用户在 `kr_assignments` 中作为负责人的有效 KR。
- 多负责人 KR 对所有被分配负责人均可见，不再使用 KR 的单一 `ownerId` 或项目关系进行二次过滤。
- 已归档 KR 不允许用于新日报，但编辑历史日报时必须保留原关联信息并正常显示。
- 选择 KR 后，由 KR 自动确定 Objective 和项目，用户不能为该工作项另选项目。

### 2. 不关联 KR 时的项目归属

- 选择“不关联 KR”后，必须选择“所属项目”。
- 可选项目仅限当前用户参与或负责的项目。
- 如果用户既没有可关联 KR，也没有任何可选项目，则不能提交日报，并提示联系项目负责人或管理员完成项目分配。
- 后端必须独立校验项目成员关系，不能只依赖前端下拉框限制。

### 3. 一天内多组日报

- 每个 Daily OKR 工作组独立保存 `linkedKeyResultId` 和 `projectId`。
- 同一天的不同工作组可以关联不同 KR 或不同项目。
- “添加另一组 OKR”按钮始终显示。
- 当前组必填项未完成时按钮禁用，并显示“请先完成当前组必填内容”。
- 当前组完成后按钮自动启用；点击后新增一组空白工作项。

## 工时可见范围

| 角色 | 可查看范围 |
| --- | --- |
| 普通员工 | 仅本人全部工时 |
| 项目负责人 | 本人全部工时，以及其负责项目内成员归属于这些项目的工时 |
| 管理层 | 维持现有组织级工时权限 |
| HR | 维持已确认的 HR 专属工时总览及隐私限制 |

补充规则：

- 项目负责人负责多个项目时，默认合并展示这些项目的数据，并可按项目筛选。
- 同一员工参与多个项目时，每条工作记录只按其 KR 所属项目或显式选择的项目计入一次，禁止重复统计。
- 关联 KR 的工作项使用 KR 所属项目作为工时归属。
- 不关联 KR 的工作项使用员工显式选择的项目作为工时归属。
- 历史数据中既未关联 KR、也没有项目归属的记录不得猜测归属。员工本人及已有组织级权限者仍可查看；项目负责人不能通过项目权限查看这些记录。

## 权限模型

### KR 候选权限

日报候选 KR 的判定以 `kr_assignments` 为唯一负责人事实来源。前端不得在完成分配查询后，再通过只理解单一 `ownerId` 的通用读取权限过滤器删除候选项。

读取 OKR 摘要的通用权限与“是否可以把该 KR 关联到自己的日报”是两个相关但不同的能力：日报关联能力要求当前用户是该 KR 的有效负责人；不能用项目可见性替代负责人校验。

### 工时读取权限

工时读取应基于每个日报工作项的项目归属计算：

1. 当前用户是记录作者时允许读取。
2. 当前用户是该工作项归属项目的项目负责人时允许读取。
3. 管理层与 HR 按现有已确认策略读取。
4. 其他情况拒绝读取。

前端过滤用于展示，Supabase RLS 或受控查询必须执行同等的服务端约束，避免仅靠界面隐藏数据。

## 数据与提交流程

每个日报工作项提交时遵循以下互斥流程：

```text
选择已分配 KR
  -> 校验当前用户仍是 KR 负责人
  -> 从 KR 解析 Objective 与项目
  -> 保存 KR、Objective、项目归属

选择不关联 KR
  -> 要求选择所属项目
  -> 校验当前用户参与或负责该项目
  -> 保存空 KR、空 Objective、显式项目归属
```

若在打开表单后用户的 KR 或项目分配被撤销，提交必须失败并给出可操作提示，而不是保存失效关联。

## 页面行为

### 日报页面

- KR 下拉框显示“不关联 KR”及本人被分配的有效 KR。
- 选择 KR 时展示只读的 Objective/项目上下文。
- 选择“不关联 KR”时展示必填项目下拉框。
- 无项目可选时展示明确空状态，不提供越权项目。
- 新增第二组后，各组独立校验和提交。

### 仪表盘工时视图

- 普通员工不显示无权限的成员筛选；数据固定为本人。
- 项目负责人可在“本人及所负责项目成员”范围内按成员、项目、日期、Objective、KR 和季度筛选。
- 汇总小时数、成员数和记录数必须基于同一组已授权且去重后的记录计算。
- 无归属历史记录对作者可标记为“未归属项目”，但不进入项目负责人的团队统计。

## 错误处理

- KR 分配已失效：提示“该 KR 已不再分配给你，请重新选择”。
- 项目成员关系已失效：提示“你已不属于该项目，请重新选择或联系管理员”。
- 未关联 KR 且未选择项目：提示“请选择所属项目”。
- 没有任何可选项目：提示联系项目负责人或管理员进行项目分配。
- 服务端权限拒绝不得被转化为“暂无数据”；页面应展示加载失败或权限错误，以便区分真正的空状态。

## 兼容性与迁移

- 不对历史无项目记录做推测性回填。
- 现有已关联 KR 的记录可通过 KR 解析项目；若数据库已有持久化项目字段，以有效关联的 KR 项目为准并检查不一致数据。
- 新建的不关联 KR 记录必须具有项目归属，因此需要数据库约束、RPC 校验或等效的服务端校验。
- 迁移必须使用向前迁移，不修改已部署迁移。

## 测试与验收

至少覆盖以下场景：

1. 用户是多人负责 KR 的其中一人，即使不是旧的单一 owner，也能在日报下拉框看到并关联该 KR。
2. 未分配给用户的 KR 不出现在候选项中，伪造提交被服务端拒绝。
3. “不关联 KR”始终为第一项，并要求选择用户参与或负责的项目。
4. 用户不能提交其他项目的 ID；分配在表单打开后撤销时提交失败。
5. 普通员工只能查看本人工时。
6. 项目负责人能查看本人全部工时和所负责项目成员归属于这些项目的工时，但看不到其他项目工时。
7. 多项目、多负责人场景不重复统计同一工作项。
8. 历史无项目记录对作者仍可见，但不进入项目负责人的团队视图。
9. “添加另一组 OKR”始终可见，未完成时禁用并提示，完成后可新增第二组。
10. 两组日报可分别关联不同 KR 或项目，并正确保存与汇总。
11. 已归档 KR 不出现在新建候选项中，历史编辑仍能显示原值。
12. HR 与管理层现有权限和隐私边界无回归。
13. Supabase 权限错误在页面上显示为错误，而不是空数据。

## 不在本次范围内

- 不新增组织汇报线或直属上级数据模型。
- 不允许所有项目负责人查看全组织员工工时。
- 不修改已确认的 HR OKR 创建、多人负责人和 KR 创建规则。
- 不对历史无归属工时进行自动项目推断。
